A-014 Prisma's query API cannot construct PostGIS geometries directly, so GPS-bearing tables (Location, GPSPoint, RouteTrace) store lat/lng as Decimal columns (source of truth for the app layer) plus a PostGIS `geography(Point,4326)` column kept in sync by a database trigger, so PostGIS distance/containment queries are genuinely usable from day one without forcing raw SQL into every write path.
A-015 Postgres Row-Level Security is implemented as the third isolation layer (spec risk #7) on every table carrying `client_id`, fail-closed (no `app.tenant_id` session setting = zero rows visible). It is applied automatically by a migration that walks `information_schema` rather than hand-listing ~30 tables, so it can't silently miss a new tenant-scoped table added later.
A-016 `docker-compose.yml` pulls images via `mirror.gcr.io/...` (Google's public Docker Hub pull-through cache) instead of `docker.io/...` directly, because this build container's egress policy blocks Docker Hub's CDN backend (`production.cloudfront.docker.com`, 403). `mirror.gcr.io` is a public mirror usable from any machine, so this is not a workaround that needs to be undone for the founder's own machine — it works the same way there.
A-018 BUG FOUND AND FIXED during Phase C end-to-end testing (not hypothetical — reproduced live): Postgres placeholder GUCs (custom settings like `app.tenant_id` that are never declared in postgresql.conf) revert to an empty string `''`, not `NULL`, once a `SET LOCAL` that touched them goes out of scope. Because Prisma's connection pool reuses physical connections across unrelated requests, any pooled connection that had run `runInTenantContext(...)` at least once would then throw `invalid input syntax for type uuid` on its very next `runWithBypass(...)` call (a totally unrelated request), because `''::uuid` errors. Fixed in migration `fix_rls_empty_string_guc` by wrapping the RLS policy's cast in `NULLIF(current_setting(...), '')::uuid`, and defensively in `PrismaService.runWithBypass` by explicitly clearing `app.tenant_id` too. Caught by driving the actual multi-role-across-campaigns scenario (Sneha Reddy) through a real browser via Playwright, not by unit-level checks — the lesson generalizes: this class of bug only surfaces under connection reuse across two different tenant-context code paths in sequence.
A-017 KNOWN LIMITATION, not just an assumption: spec §34's entity list has only one role-assignment table, UserCampaignRole, which is always campaign-scoped. It has no way to express "this person has a platform-wide role that isn't tied to any single campaign" (Super Admin, Impact System Administrator, Auditor, etc. per spec §8's "Platform" role category). The seed script works around this by giving platform-category users a UserCampaignRole row on every seeded campaign — functionally workable for a demo, but not a real platform-role model. A future feature module should either add a nullable campaignId to UserCampaignRole (platform grant when null) or a separate OrganisationRole table, plus a corresponding RLS/permission-guard path — flagging now rather than silently baking the workaround in as if it were the intended design.
