A-018 BUG FOUND AND FIXED during Phase C end-to-end testing (not hypothetical — reproduced live): Postgres placeholder GUCs (custom settings like `app.tenant_id` that are never declared in postgresql.conf) revert to an empty string `''`, not `NULL`, once a `SET LOCAL` that touched them goes out of scope. A-025 BUG FOUND AND FIXED during Stage 2 Session A's form-builder verification (reproduced live via curl and a browser test, not hypothetical): `FormsService.upsertDraft` and `.publish` each ended by calling `this.findOne(...)`, which opens its own `PrismaService.runInTenantContext(...)` — a brand-new `$transaction(...)` — from *inside* the caller's own still-open transaction. Prisma's interactive transactions reserve a dedicated connection for their duration, so the nested call runs on a second connection; under ordinary Postgres MVCC, that second transaction's snapshot cannot see the first (still-uncommitted) transaction's writes. The practical effect: publishing a form, or saving a draft, appeared in the API response to have silently done nothing (0 sections, 1 stale version) even though the write had genuinely happened moments earlier and a subsequent, separate GET showed it correctly. Fixed by extracting `loadTemplateTree(tx, ...)`, which takes an already-open transaction client instead of opening a new one; `upsertDraft`/`publish` now call it with their own `tx`, and only the standalone `findOne(...)` (never called from inside another transaction) opens a fresh one. Checked the rest of the backend for the same shape (`this.<methodThatOpensATransaction>(...)` called from inside another transaction's callback) — no other instance found; `ClientsService.update`'s call to `this.findOne(id)` looked similar but is sequential (the first transaction fully commits before the second starts), which is safe.

A-027 Platform-level campaign creation (`POST /campaigns`) is gated on the `edit` permission, not the generic `create` permission, even though "create" reads more naturally for "create a campaign." The `create` permission code is also held by field roles (Promoter, Field Executive, Vendor) for creating field records like activity submissions — an entirely different capability that happens to share a name. Reusing it for platform-level campaign creation would have let a Promoter create campaigns. `edit` is scoped correctly (Campaign Manager, Project Manager, Data Administrator, platform admins — the roles the seed already treats as "people who configure campaigns") and is the same permission already required for campaign updates and status transitions, so this also avoids introducing a new permission code for no reason. The same reasoning is why the Clients module (A-013 onward's sibling work) uses a dedicated `manage_clients` permission rather than reusing `create`/`edit`: client management has no natural existing permission that isn't ambiguous across roles, so a new dedicated code was the right call there, while campaign creation could safely reuse `edit`.

A-034 BUG FOUND AND FIXED during the founder's first real-device field-flow test (reported as "Internal Server Error after the picture is clicked," photo capture feeling "slow and laggy," and check-out then refusing to complete): `ExecutionService.uploadMedia` ran the entire MinIO upload + sharp watermark-compositing pipeline *inside* a Prisma interactive transaction (`runInTenantContext`), which defaults to a 5-second timeout. A-036 BUG FOUND AND FIXED, root cause confirmed from the founder's actual backend log (the stack trace requested in A-034): the "Internal Server Error" on photo sync was `Error: Image to composite must have same dimensions or smaller`, thrown from `MediaStorageService.renderWatermark`. Root cause: `sharp(buffer).rotate()` (auto-orient from EXIF) was queued on the pipeline, but `.metadata()` was then read on that *unresolved* pipeline — `.metadata()` always reports the file's raw, pre-rotation pixel dimensions regardless of operations queued after it, so for a portrait phone photo (landscape sensor data + an EXIF orientation tag, the overwhelmingly common case for a real phone held vertically — never seen with desktop test images, which typically carry no orientation tag), the watermark SVG strip was sized to the *wrong, pre-swap* width while `.rotate()`'s actual pixel output had width/height transposed, so the overlay no longer fit. Fixed by materializing the rotated image into a buffer first (`sharp(buffer).rotate().toBuffer()`), then reading dimensions from *that* buffer — genuinely post-rotation. Reproduced and confirmed standalone (outside the running backend, since this sandbox has no Docker daemon to run the full stack): built a synthetic 1600×1200 image carrying an EXIF orientation-6 tag (the same shape as the founder's device: landscape sensor, portrait EXIF flag) and ran both the old and new `renderWatermark` logic against it directly through the installed `sharp` package — the old code reproduced the exact same `Image to composite must have same dimensions or smaller` error message from the founder's log; the new code succeeded, correctly outputting 1200×1600 (width/height swapped, as expected after rotation). `tsc --noEmit` clean on the backend. This closes the second, previously-unconfirmed issue flagged at the end of A-034/A-035.
A-037 ROBUSTNESS GAP FOUND during continued real-device testing after A-036: a photo upload that hit a network-level connection abort (`SocketException: Software caused connection abort`, errno 103 — occurring between the phone and the founder's Mac over real Wi-Fi, with no corresponding entry in the backend log at all, meaning the connection dropped before ever reaching the server) left the outbox item stuck showing `syncing` indefinitely, still displaying the *previous* attempt's stale error text, because `ApiClient` had no request timeout at all and `OutboxDatabase.markSyncing` never cleared the old `errorMessage`. The combination made a stuck request indistinguishable from a genuinely-in-progress one, and gave no path back to a retryable `failed` state. Fixed: added a 30s timeout to ordinary JSON requests and a 60s timeout to photo uploads (`ApiClient`, via `.timeout()`), and `markSyncing` now clears `errorMessage` so a fresh attempt is never shown next to leftover text from an old one. ## Founder diagnosis and fix pass (after real-device testing exposed A-034 through A-037's gaps)

The founder tested Session B end-to-end on a real phone and diagnosed three real problems beyond A-034/A-037, correctly identifying that Session B's implementation had taken shortcuts against the *already-approved* `docs/architecture/05-offline-sync-design.md` rather than building to it. Each was independently verified (not taken on faith) before fixing — see each entry below for how.

A-038 BUG FOUND AND FIXED (founder diagnosis, confirmed from the founder's own screenshots): check-out could be attempted, and rejected by the server ("needs at least 1 photo(s) — 0 uploaded so far"), before its own milestone's photo had synced. Two compounding root causes: (1) `OutboxDatabase.pendingOrFailedItems()` had no `ORDER BY` at all, so which item the sync loop visited first was unspecified by SQL semantics; (2) even with ordering, nothing actually enforced that a check-out must wait for its own activity's other unsynced items. Fixed with both a deterministic base ordering (`ORDER BY createdAt ASC`) and, more importantly, an explicit dependency check in `SyncService.syncPending()`: a `checkOut` item is skipped (left `pending`, never attempted and never marked `failed`) for as long as any other item for the same `activityInstanceId` is still pending/failed; once cleared it's attempted, including within the same pass if its dependency happened to sync moments earlier in that same loop. Verified with two real tests (`app/test/sync_service_ordering_test.dart`, run against a genuine in-memory Drift/SQLite database, not a mock): one enqueues check-out *before* its photo (the adversarial ordering) and asserts the fake repository's `checkOut()` — which throws the exact same rejection the real backend does — is never called while the photo is unsynced; the other proves the normal chronological case (photo enqueued first) settles in one pass. Note found and worked around while writing the first test: this sandbox's Drift/SQLite setup stores `DateTime` columns at whole-second precision, so two items enqueued within the same wall-clock second can tie on `createdAt` — the dependency check is written to be correct regardless of which one a tie resolves to first (it looks at the full unsynced-sibling set, not iteration order), and the tests assert that safety property rather than one specific pass count.

A-039 DESIGN GAP FOUND AND FIXED (founder diagnosis, confirmed by reading `docs/architecture/05` directly before changing anything): Session B shipped a single-shot photo upload (one multipart POST, no retry-from-partial-progress) even though `docs/architecture/05`'s "Upload strategy" §2 explicitly specifies chunked, resumable media — `POST /media/init` (hash+size) → 512KB chunks → `complete` (server re-verifies hash), interrupted uploads resume at the last confirmed chunk — and the schema's `SyncStatus` enum (`UPLOADING`, `PARTIALLY_UPLOADED`, etc.) was already built for exactly this and simply unused by the single-shot implementation. This is very likely the real explanation for A-037's still-unexplained `SocketException ... errno 103` mid-transfer failures: a single-shot upload has no way to recover from a dropped connection except discarding the whole file and starting over, repeatedly, with the client never able to tell the server "I already sent you most of this." Implemented the approved design: a new `MediaUploadSession` model (migration `20260715133316_media_upload_sessions`, generated via `prisma migrate diff` against a schema snapshot since this sandbox has no live Postgres to diff against directly — see A-012 posture; re-runs the same RLS-enabling DO block from `rls_and_app_role` per that migration's own documented convention for new `clientId`-bearing tables) tracking `receivedChunks`, staged chunk bytes on local disk (transient, cleaned up on completion — deliberately not in Postgres or MinIO, which aren't the right home for bytes that may never finish arriving); three new endpoints (`.../media/init`, `.../media/sessions/:id/chunks/:index`, `.../media/sessions/:id/complete`) replacing the old single-shot `POST .../media`; `/init` is idempotent on the file's content hash, so a client resuming after any failure — including a fresh app launch — finds the same session and only re-sends chunks the server doesn't already have. Also implemented the doc's "exponential backoff with jitter (30s → 2m → 10m → 30m, cap 6h)" for automatic retries (`SyncService`, new `retryCount`/`nextRetryAt` columns, Drift schema v2 with a proper `onUpgrade` migration) — an explicit "Sync now" tap bypasses backoff (`force: true`), since a user pressing a button wants an answer now. Partially implemented, honestly scoped: "bind the upload to the network it started on where the platform allows" — true OS-level socket binding needs native Android platform code (`ConnectivityManager.bindProcessToNetwork` or equivalent) that this pass does not add; instead, each chunk upload checks connectivity type before and after the transfer and aborts with a specific, diagnosable error if it changed mid-flight (Wi-Fi↔mobile data), which the resumable design then retries cleanly — a reasonable approximation given available Flutter tooling, not the literal requirement, and flagged here rather than silently claimed as done. Verified: the chunk-staging mechanism itself (`MediaStorageService.writeChunk`/`assembleChunks`/`discardChunks`) was exercised directly with a standalone script — wrote three chunks *out of order*, re-wrote one to simulate a re-sent/duplicate chunk, assembled, and confirmed the result's SHA-256 exactly matches the original 1.25MB buffer, then confirmed cleanup removes the staging directory. `tsc --noEmit` clean on the backend; `flutter analyze`/`build linux`/`test` clean on the app. What remains unverified in this sandbox (no Docker/Postgres/MinIO running, no camera/GPS hardware — same posture as A-012/A-032): the full endpoint-to-endpoint flow against a live server, and the actual real-Wi-Fi-drop resumption on the founder's phone — needs the founder's next real-device test to confirm.

A-041 REGRESSION INTRODUCED AND FIXED — my own mistake, found live on the founder's phone within minutes of them retesting: migration `20260715133316_media_upload_sessions` (A-039) re-ran the RLS-enabling DO block that walks every `clientId`-bearing table and rebuilds its `tenant_isolation` policy — the *correct*, documented practice per `rls_and_app_role`'s own comment for any migration adding a new tenant-scoped table. The mistake: I copied that DO block from the **original** `rls_and_app_role` migration instead of the **fixed** version in `fix_rls_empty_string_guc` (A-018), which wraps the policy's `current_setting('app.tenant_id', true)` in `NULLIF(..., '')` before casting to `uuid`. Since my migration ran chronologically after the fix, it silently overwrote every table's policy back to the pre-fix, buggy version — reintroducing A-018's exact bug (`invalid input syntax for type uuid: ""` on a pooled connection reused between a tenant-scoped call and a bypass call) for the whole database, not just the new table. Lesson for future migrations that need to re-run this DO block: copy it from the *latest* migration that defines it correctly (currently `fix_rls_empty_string_guc`, until superseded), never from memory or from the first migration that introduced the pattern.
A-042 BUG FOUND AND FIXED during the founder's airplane-mode test (reproduced live: a screenshot showing the whole Activity screen replaced by a raw `ClientException with SocketException: Network is unreachable`): `ActivityDetailScreen._load()` is called again after every offline-capable action (returning from the camera screen, returning from the milestone form, after check-in/check-out) to pick up any server-side changes — and while genuinely offline, that refresh call is *expected* to fail. Verified via `flutter analyze` (0 issues), `flutter build linux`, `flutter test` (all passing).

A-046 Stage 3.1 design decisions made within the session (per process rule 1 — practical assumption, logged, not asked):
- **SkuMovementType is the build-sequence's 7-value list** (OPENING_STOCK, RECEIVED, SOLD, FREE_SCHEME, SAMPLED, DAMAGED, CLOSING_STOCK_ACTUAL), with `quantity` and `amount` as columns on each movement row — the report-format-library §3 table's separate `SOLD_QTY`/`SOLD_AMOUNT` (and `FREE_SCHEME_QTY`/`FREE_SCHEME_VALUE`) entries map to the qty/amount columns of one movement type, matching the same doc's own proposed row shape `(movementType, quantity, amount)`.
- **A quantity answer and its amount answer write two additive movement rows** (qty row with amount NULL, amount row with quantity 0) rather than being merged into one row at submission time — every consumer (DFR rollup, §22 reconciliation) does SUM() per type, for which additive rows are arithmetically identical, and submission stays a simple per-field walk.
- **The DFR archetype preset builds a day-summary record form**, not a "type the totals" form: report-format-library §2 mandates the DFR *view* is always a rollup query. For campaigns whose natural record IS team/day (a mela stall's single daily count), day-level is the record level; campaigns with outlet granularity use the PROFILE preset and get their DFR purely from the rollup endpoint. The preset's own "Totals" section is AUTO_CALCULATED (formula-driven), so even the day-summary form never has a typed total.
- **FREE_SCHEME is excluded from expected-closing** in the §22 reconciliation formula, exactly as report-format-library §3 annotates ("scheme, not in §22 formula — additive") — it is reported alongside, never subtracted. If physical reality on a real campaign disagrees (scheme stock does leave the van), this is a one-line change in `expectedClosingStock()` and its tests.
- **Stock-mismatch exceptions are created at submission time** (when a CLOSING_STOCK_ACTUAL movement arrives), not by the report endpoint — a report view that mutates state on read would fire duplicate exceptions on every page load. Full exception lifecycle (assignment, escalation, closure) remains Stage 5.2.
- **`FieldType` gained `AUTO_CALCULATED`** — the workbook's formula columns ("Total Qty", "Total Sales Amt.") had no existing enum value; the AUTO_* family per §4 was for server-known identity/time values. Formulas use a deliberately tiny safe grammar (`SKU_QTY_TOTAL(type)`, `SKU_AMOUNT_TOTAL(type)`, arithmetic, no eval, validated at draft-save time).
- **SKU-bound questions carry their binding in `controlsJson.skuBinding`** ({campaignSkuId, movementType, metric}) rather than a new FK column on FormQuestion — the binding is form-version-frozen configuration exactly like every other per-field control, and gets cloned/frozen by publish the same way (which is what makes acceptance test §5.4 pass naturally).
- **SKU management shares the `manage_forms` permission** — the SKU master exists to feed per-SKU form questions; a separate permission code would add a role-matrix row with no real-world role that has one but not the other.
