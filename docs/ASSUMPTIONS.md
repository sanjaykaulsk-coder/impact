A-025 BUG FOUND AND FIXED during Stage 2 Session A's form-builder verification (reproduced live via curl and a browser test, not hypothetical): `FormsService.upsertDraft` and `.publish` each ended by calling `this.findOne(...)`, which opens its own `PrismaService.runInTenantContext(...)` — a brand-new `$transaction(...)` — from *inside* the caller's own still-open transaction. Prisma's interactive transactions reserve a dedicated connection for their duration, so the nested call runs on a second connection; under ordinary Postgres MVCC, that second transaction's snapshot cannot see the first (still-uncommitted) transaction's writes. The practical effect: publishing a form, or saving a draft, appeared in the API response to have silently done nothing (0 sections, 1 stale version) even though the write had genuinely happened moments earlier and a subsequent, separate GET showed it correctly. Fixed by extracting `loadTemplateTree(tx, ...)`, which takes an already-open transaction client instead of opening a new one; `upsertDraft`/`publish` now call it with their own `tx`, and only the standalone `findOne(...)` (never called from inside another transaction) opens a fresh one. Checked the rest of the backend for the same shape (`this.<methodThatOpensATransaction>(...)` called from inside another transaction's callback) — no other instance found; `ClientsService.update`'s call to `this.findOne(id)` looked similar but is sequential (the first transaction fully commits before the second starts), which is safe.

A-027 Platform-level campaign creation (`POST /campaigns`) is gated on the `edit` permission, not the generic `create` permission, even though "create" reads more naturally for "create a campaign." The `create` permission code is also held by field roles (Promoter, Field Executive, Vendor) for creating field records like activity submissions — an entirely different capability that happens to share a name. Reusing it for platform-level campaign creation would have let a Promoter create campaigns. `edit` is scoped correctly (Campaign Manager, Project Manager, Data Administrator, platform admins — the roles the seed already treats as "people who configure campaigns") and is the same permission already required for campaign updates and status transitions, so this also avoids introducing a new permission code for no reason. The same reasoning is why the Clients module (A-013 onward's sibling work) uses a dedicated `manage_clients` permission rather than reusing `create`/`edit`: client management has no natural existing permission that isn't ambiguous across roles, so a new dedicated code was the right call there, while campaign creation could safely reuse `edit`.

A-034 BUG FOUND AND FIXED during the founder's first real-device field-flow test (reported as "Internal Server Error after the picture is clicked," photo capture feeling "slow and laggy," and check-out then refusing to complete): `ExecutionService.uploadMedia` ran the entire MinIO upload + sharp watermark-compositing pipeline *inside* a Prisma interactive transaction (`runInTenantContext`), which defaults to a 5-second timeout. A-036 BUG FOUND AND FIXED, root cause confirmed from the founder's actual backend log (the stack trace requested in A-034): the "Internal Server Error" on photo sync was `Error: Image to composite must have same dimensions or smaller`, thrown from `MediaStorageService.renderWatermark`. Root cause: `sharp(buffer).rotate()` (auto-orient from EXIF) was queued on the pipeline, but `.metadata()` was then read on that *unresolved* pipeline — `.metadata()` always reports the file's raw, pre-rotation pixel dimensions regardless of operations queued after it, so for a portrait phone photo (landscape sensor data + an EXIF orientation tag, the overwhelmingly common case for a real phone held vertically — never seen with desktop test images, which typically carry no orientation tag), the watermark SVG strip was sized to the *wrong, pre-swap* width while `.rotate()`'s actual pixel output had width/height transposed, so the overlay no longer fit. Fixed by materializing the rotated image into a buffer first (`sharp(buffer).rotate().toBuffer()`), then reading dimensions from *that* buffer — genuinely post-rotation. Reproduced and confirmed standalone (outside the running backend, since this sandbox has no Docker daemon to run the full stack): built a synthetic 1600×1200 image carrying an EXIF orientation-6 tag (the same shape as the founder's device: landscape sensor, portrait EXIF flag) and ran both the old and new `renderWatermark` logic against it directly through the installed `sharp` package — the old code reproduced the exact same `Image to composite must have same dimensions or smaller` error message from the founder's log; the new code succeeded, correctly outputting 1200×1600 (width/height swapped, as expected after rotation). `tsc --noEmit` clean on the backend. This closes the second, previously-unconfirmed issue flagged at the end of A-034/A-035.
A-037 ROBUSTNESS GAP FOUND during continued real-device testing after A-036: a photo upload that hit a network-level connection abort (`SocketException: Software caused connection abort`, errno 103 — occurring between the phone and the founder's Mac over real Wi-Fi, with no corresponding entry in the backend log at all, meaning the connection dropped before ever reaching the server) left the outbox item stuck showing `syncing` indefinitely, still displaying the *previous* attempt's stale error text, because `ApiClient` had no request timeout at all and `OutboxDatabase.markSyncing` never cleared the old `errorMessage`. ## Founder diagnosis and fix pass (after real-device testing exposed A-034 through A-037's gaps)

The founder tested Session B end-to-end on a real phone and diagnosed three real problems beyond A-034/A-037, correctly identifying that Session B's implementation had taken shortcuts against the *already-approved* `docs/architecture/05-offline-sync-design.md` rather than building to it. Each was independently verified (not taken on faith) before fixing — see each entry below for how.

A-038 BUG FOUND AND FIXED (founder diagnosis, confirmed from the founder's own screenshots): check-out could be attempted, and rejected by the server ("needs at least 1 photo(s) — 0 uploaded so far"), before its own milestone's photo had synced. Two compounding root causes: (1) `OutboxDatabase.pendingOrFailedItems()` had no `ORDER BY` at all, so which item the sync loop visited first was unspecified by SQL semantics; (2) even with ordering, nothing actually enforced that a check-out must wait for its own activity's other unsynced items. Fixed with both a deterministic base ordering (`ORDER BY createdAt ASC`) and, more importantly, an explicit dependency check in `SyncService.syncPending()`: a `checkOut` item is skipped (left `pending`, never attempted and never marked `failed`) for as long as any other item for the same `activityInstanceId` is still pending/failed; once cleared it's attempted, including within the same pass if its dependency happened to sync moments earlier in that same loop. Verified with two real tests (`app/test/sync_service_ordering_test.dart`, run against a genuine in-memory Drift/SQLite database, not a mock): one enqueues check-out *before* its photo (the adversarial ordering) and asserts the fake repository's `checkOut()` — which throws the exact same rejection the real backend does — is never called while the photo is unsynced; the other proves the normal chronological case (photo enqueued first) settles in one pass. A-061 Stage 4.2 (Flutter continuous GPS + on-device deviation warning) design decisions and deferrals, made within the session (per process rule 1):
- **Tracking is foreground-only, not a true Android background service.** A survey of `app/lib` before starting confirmed this app has never had any continuous/background location capture — only one-shot fixes at check-in, check-out, and photo capture. A-064 Web login-refresh race condition — found by the founder while testing S4.2's Device Risk page, root-caused and fixed same session, not a design decision but logged per the same discipline as every other found-and-fixed bug in this file:
- **Symptom, as the founder reported it**: clicking "Clear" on a flagged device intermittently showed a red "Could not clear this device" error. Backend terminal logs showed nothing abnormal (expected — a clean 4xx isn't a crash). A browser DevTools screenshot the founder took at my request showed the real underlying response: a genuine `401 Unauthorized` from the API. Signing out and back in did not fix it ("No change"). Two further screenshots proved the session was demonstrably fresh and valid (a clean, error-free page load) immediately before Clear still failed identically — ruling out ordinary token expiry as the explanation.
- **Root cause**: `backend/src/modules/auth/token.service.ts`'s `rotate()` deliberately makes refresh tokens single-use — each successful `/auth/refresh` call revokes the presented token and issues a new pair. `web/src/lib/api.ts`'s automatic 401-retry logic (`tryRefresh()`) had no protection against being called twice at once. If two API calls both got a 401 around the same moment — plausible on a page that both loads data on mount and lets the user click a button — each read the same soon-to-be-superseded refresh token from `localStorage` and raced to `/auth/refresh` independently. The one that lost the race presented an already-used token, got rejected, and called `tokenStore.clear()` — deleting the *other* call's freshly-issued, perfectly valid tokens. Net effect: the founder gets silently signed out mid-action, with the only visible symptom being a 401 on whatever request happened to be "the loser."
- **This was never specific to Device Risk or to Clear** — any two near-simultaneous API calls on any page could have triggered it. Device Risk just happened to be the first page tested where a background load and a manual click could realistically overlap.
- **Fix**: `tryRefresh()` now returns a shared in-flight promise (`refreshInFlight`) instead of always starting a new refresh — every concurrent caller within the same refresh window awaits and receives the result of the exact same single `/auth/refresh` call, so there is no longer a "loser" that clears a winner's valid session.
- **Verified**: `tsc --noEmit` clean in `web/`; `next build` clean (all 18 routes, including `/dashboard/device-risk`, compiled and prerendered without error). Not yet re-confirmed on the founder's own machine at the time of this entry — that confirmation is the next step, same as every other founder-facing fix in this project.

A-078 Post-MVP backlog, fourth item — perceptual duplicate detection (spec §17/§18; docs/architecture/08 §5: "exact-hash duplicates in MVP; perceptual similarity post-MVP"), per process rule 1:
- **Plugs into the existing device-risk signal pipeline (S4.2) rather than inventing a new one.** `DeviceRiskService.recordSignal()` already existed with exactly the right shape (escalate a device's risk level, write an Alert, never downgrade) for two signals (`DEVICE_TIME_MISMATCH`, `MOCK_LOCATION_SUSPECTED`) — this adds a third, `DUPLICATE_MEDIA_SUSPECTED`, defaulted to `L2_FLAGGED` (a real, worth-a-look signal per spec's own "old photograph" risk type, but with enough innocent explanations — two visits to a genuinely similar-looking stall — that it's flagged for review, not restricted outright, matching the reasoning already used for the time-mismatch signal).
- **A real perceptual hash (dHash), not a placeholder.** A 64-bit difference hash computed via `sharp` (already a dependency, already used for watermarking) — resize to 9×8 greyscale, record whether each pixel is brighter than its right-hand neighbour. No ML model, no external service, no new dependency. Empirically validated with real generated images before trusting it in the upload flow: a re-compressed copy of the same photo → Hamming distance 0; a lightly cropped copy → distance 10 (right at the chosen threshold, correctly still flagged); a genuinely different photo → distance 26 (correctly not flagged). The threshold (≤10 out of 64 bits) is the standard rule of thumb for this exact algorithm, not an invented number.
- **Comparison is scoped to the same uploader within the same campaign, most recent 200 photos** — bounded so it stays fast as a campaign's media grows, and matches the actual risk scenario spec §18 names ("old photograph": reusing a photo across different real-world visits), not exhaustive whole-database comparison.
- **New nullable `Media.perceptualHash` column** (a straightforward additive migration, no RLS changes needed since it's a column on an already-RLS-enabled table, not a new table) — computed best-effort at upload completion; a hash failure (unexpected format) never blocks the actual photo upload, it just means that one photo isn't compared against past ones.
- **Verified end-to-end against the real running backend, not just unit-level**: wrote a throwaway test script (not committed) that logged in as a real seeded user, checked into a real activity, and uploaded three real photos through the actual chunked-upload API — an original, a re-compressed near-duplicate (different bytes, different file size, same visual content), and a genuinely different photo. Confirmed: the near-duplicate correctly raised exactly one `DUPLICATE_MEDIA_SUSPECTED` alert (Hamming distance 0, both media IDs and the matched activity referenced in the alert's evidence, device risk level escalated to `L2_FLAGGED`) and the genuinely different photo correctly raised none — both a true positive and a checked-for false positive, not just the happy path. All test media, the test alert, and the device's risk level were removed/reset afterward; the activity used for testing (the founder's own "Founder Phone Test Stop") was reverted to its pre-test check-in state so it's still available for future testing.
- **Web-side**: the general Alerts inbox (S5.2) already displays any `issueType` generically, no changes needed. The Device Risk page (S4.2) has a small friendly-label lookup table for known signal types (falls back to the raw enum name otherwise) — added a label for this one so it reads "Photo looks like a re-used/old photograph" rather than the raw constant.
